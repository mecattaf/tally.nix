# Authoring a flow

A tally flow is deterministic JavaScript that submits ordinary tally jobs. The
JavaScript decides *which* node comes next; the daemon decides *when* and *where*
each node runs. The flow is not one schedulable bundle of all its children.

That distinction is the useful mental model:

- Control flow is replayed deterministic code.
- A node is opaque, impure work executed by an adapter and executor.
- Pools, priorities, leases, evidence, and terminal verdicts belong to nodes.
- `await` observes a witnessed terminal fact. It does not keep the child's lease.

The runner is itself an ordinary job and, when generated by the Home Manager
module, holds the reserved `flow` pool for its lifetime. Its child jobs hold their
own workload pools only while they run. Between two child nodes the flow holds no
GPU, build, model, or other child-workload lease. A calendar job or an
interrupt-priority task can therefore win admission before the next node; the
script simply experiences a longer `await`.

There is no flow pause or resume operation. A child that has not yet been admitted
holds nothing to pause, and a completed child has already released its lease.
Restart recovery comes from replaying the script, not from restoring a suspended
JavaScript heap. See [Submission identity and replay](submission-and-replay.md).

## Make the node the atomic unit

Interleaving happens at node boundaries, so put one independently retryable and
witnessable action in each node. Do not put an entire campaign in one shell node
merely to keep a resource. That would hide the internal evidence and prevent the
scheduler from admitting other work between stages.

Conversely, do not split an operation at a point where another node cannot safely
observe its result. A good node either publishes its output atomically or leaves a
failure that a later run can recognize. Use `await` for a prerequisite:

```javascript
const built = await sh([args.builder, args.manifest], {
  pools: ["build-host"],
  key: "build",
  evidence: ["exit:0", `artifact:${args.output}`, "hash:sha256"]
});

return sh([args.publisher, built.result.digest], {
  pools: ["network-egress"],
  key: "publish",
  evidence: ["exit:0"]
});
```

The second node is not materialized if the first promise rejects. With
`{ settle: true }`, a failed node is returned as data and the script must make the
next decision explicitly.

Two current limits matter when choosing pools:

- There is no supported way for a flow to co-lease a workload mutex for the whole
  runner lifetime. The generated runner requests only `flow`; putting a mutex on
  individual children protects only those children. The run-wide question remains
  open in [#107](https://github.com/mecattaf/tally.nix/issues/107).
- A flow node deliberately has no `consumptionEstimate` field. Checked flows
  are excluded from `windowed-consumption` pools by design. Use low node
  priorities for wave work so a more important ask can intercede during the
  run without estimates preventing completion.

Those are descriptions of the shipped interface, not invitations to emulate a
missing run-wide lease in JavaScript.

## Put data in Nix and decisions in JavaScript

Prefer thick Nix data and thin JavaScript control. Values known while building the
host generation belong in `services.tally.flows.<name>.args`: roster-independent
paths, program paths, repositories, fixed policy, and bounded input lists. The
module serializes the attributes to JSON and validates them against
`meta.argsSchema` before activation.

The script should route that data and prior `NodeResult` values. It should not
discover configuration by reading a clock, environment variable, directory, or
network endpoint. If discovery is genuinely impure, make it a node and use its
witnessed compact result. Pass paths and digests through the flow; let workers read
or write the bytes.

The replay-safe construction rule is strict: build a node specification only from
`args`, literals, `meta`/`flowMeta`, and results already observed from earlier
nodes. A value from anywhere else cannot be re-derived reliably after a runner
crash.

## Check and register the script

Start with the checker. It prints the literal metadata as JSON on success:

```console
$ tally flow check ./flows/nightly.js --args '{"revision":"abc123"}'
{"name":"nightly",...}
```

If the flow uses selectors, the catalog is a CLI input, not an environment
variable:

```console
$ tally flow check ./flows/review.js \
    --args '{"subject":"change 42"}' \
    --catalog /nix/store/...-tally-flow-catalog.json
```

The Home Manager module turns a non-null calendar into an ordinary calendar
producer:

```nix
services.tally.flows.nightly = {
  script = ./flows/nightly.js;
  onCalendar = "daily";
  args.revision = "abc123";
  maxNodes = 20;
};
```

Building the Home Manager generation runs the real `tally flow check` binary. It
validates the literal metadata, configured arguments, declared pools, node
ceiling, and selector catalog. A bad script consequently fails `home-manager
switch` rather than its timer at night.

The implementation is narrower than the option tree suggests:

- Only the Home Manager module accepts flow entries and generates the calendar
  producer and automatic `flow` and `build` pools. The NixOS module rejects flow
  entries with a pointer to the Home Manager module.
- `onCalendar = null` creates no producer. The entry is still checked while the
  generation is built, and the script can be run directly.
- A generated runner's pool set is exactly `[ "flow" ]`. The configuration's
  `budgetPool` value is checked only to ensure that the named pool exists; it is
  not added to the runner or its children.

For an unscheduled run, supply a UUID explicitly unless tally is launching the
runner as a parent job:

```console
$ tally flow run ./flows/nightly.js \
    --flow-run-id 6ba7b810-9dad-41d1-80b4-00c04fd430c8 \
    --args '{"revision":"abc123"}' \
    --max-nodes 20
```

The explicit flag wins when present. Otherwise the runner takes `flowRunId` from
its inherited `TALLY_TASK_UUID`; a job-launched runner requires that UUID and
`TALLY_JOB_ID` together and uses them for child ancestry. Having neither identity
source is `flow-run-id-missing` (exit 2); a malformed or half-present inherited
identity also exits 2. After capturing identity, the CLI retains `TALLY_SOCKET`
but removes other inherited `TALLY_*` variables before executing the script, so
child tools cannot mistake the runner's identity for their own.

## Learn from the shipped flows

The repository keeps its executable examples under `examples/flows/`, and the
flake checks every one with `tally flow check`.

- [`agency-nightly.js`](https://github.com/mecattaf/tally.nix/blob/main/examples/flows/agency-nightly.js)
  is a compact implement-review-verify chain using Codex, Claude, and a shell
  verifier.
- [`pooled-review.js`](https://github.com/mecattaf/tally.nix/blob/main/examples/flows/pooled-review.js)
  is the complete selector, repair, quorum, and dissent pattern explained in the
  [pooled-review cookbook](pooled-review.md).
- [`fleet-deploy.js`](https://github.com/mecattaf/tally.nix/blob/main/examples/flows/fleet-deploy.js)
  is a zero-LLM cross-host handoff through Git, explained in
  [Cross-host handoff](cross-host-handoff.md).

The newer `monthly-review.js` and `academic-ocr.js` examples show store-native
`drv()` stages and a bounded mutation ladder respectively. They use the same
authoring rules; their larger graphs do not acquire a special workflow lease.
