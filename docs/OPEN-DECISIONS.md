# tally.nix — Open decisions for Tom

> Phase 0+1 surfaced **25 candidate decisions**. A 7-lens triage (frozen `DECISIONS`/`SPEC`/`CLI`+`src`, the july14 chat, prior-art, and two nix-maximalists) resolved 21 against authoritative sources — baked into the docs with citations. Two devil's-advocate waves then **audited the triage**, promoting two silently-baked over-resolutions back here. What remains is the true residue: **4 decisions only you can make.** Each carries a recommendation; the default docs already encode the recommended option, so *no answer* == *accept the recommendation*.

## CD-01 — What are the canonical NAMES of the TWO net-new witness verdict values that land, permanently, on the product-identity ledger: (a) remote-pool/broker loss mid-hold, and (b) the interrupt-tier hard-reclaim outcome? Both semantics are settled (R26: set after a hysteresis-confirmed broker-unreachable transition, excluded from canonical gpu_seconds; R29: hard-reclaim after yieldGraceSec, re-presentable) — only the two strings are unfixed.

**Options:**
- (a) pool-vanished + (b) preempted (recommended)
- (a) lease-lost / resource-unreachable / broker-lost
- (b) reclaimed / yielded / interrupted
- a different pairing

**Recommendation:** (a) pool-vanished — it names the OBSERVED condition (the pool/broker went away) rather than the internal artifact (a lease), matching the tool's evidence-first vocabulary and reading correctly for both vram and remote build-slot pools; (b) preempted — the standard scheduler term for a hard-reclaimed lower-priority holder, distinct from failed.

**Why it's genuinely open (not already settled):** The verdict enum is ported byte-for-byte (R12), but these are TWO net-new values with no analog: the Bun enum is pass|clean-exit-no-artifact|failed|cancelled|reused (src/contracts/job.ts:22), and DECISIONS/SPEC/july14 never name a lease-loss OR a preemption verdict, nor does any exemplar repo carry a resource-loss/preemption taxonomy to borrow. Because the verdict chain is the product's permanent identity, the architect surfaces both names rather than silently minting ledger vocabulary (wave-3 folded `preempted` in here after devil-2 flagged it was being baked silently while only `pool-vanished` reached Tom).

## CD-02 — The reserved top priority tier: confirm its NAME and RANK, and — the load-bearing part (devil #15) — its GUARANTEE LEVEL. On a capacity=1 pool held by a slow-to-checkpoint low job, a cooperative-only interrupt can be starved; recovery was the justifying use case.

**Options:**
- interrupt @ rank 1000, best-effort cooperative with hard-reclaim after yieldGraceSec (recommended default)
- interrupt @ 1000 with an always-on hard-preempt (kill + re-present the yielded holder immediately)
- interrupt @ 1000 plus a reserved capacity slot on designated recovery pools (a real guarantee, at idle-capacity cost)
- a different name/rank

**Recommendation:** interrupt @ rank 1000, best-effort cooperative by DEFAULT (yield-flag poll + hard-reclaim after yieldGraceSec, R29), with per-pool hard-preempt as an opt-in — this keeps the common path cooperative while letting a recovery pool declare a hard guarantee where starvation is unacceptable.

**Why it's genuinely open (not already settled):** No tier above high/medium/low exists in any frozen source (Bun hardcodes 100/50/10 in dispatch.ts:26 and preempt.ts:56) or in july14; the EXPOSURE mechanism is settled (single canonical enum, check-config-validated) but the name, the magic rank, and — critically — the guarantee semantics are a policy choice no triage lens resolved, and devil #15 shows the choice materially changes whether recovery can jump a stuck queue.

## CD-17 — Should journald emission use a native AF_UNIX SOCK_DGRAM socket client, or the existing StandardOutput=journal stdout-capture path that the frozen prototype already uses? This REVERSES a deliberately-gated jul9 decision ('flip back to native ONLY if native structured emission proves load-bearing').

**Options:**
- native AF_UNIX SOCK_DGRAM client — treat the 15-field TALLY_* structured matrix as load-bearing (architect's lean; but the frozen record disputes the premise)
- keep StandardOutput=journal stdout-capture — the frozen record (DECISIONS.md:137/SPEC.md:685) says structured TALLY_* already emit this way, and SPEC:682-684 calls journald 'observability, not load-bearing'
- native behind a toggle with the stdout path retained as fallback (BS-8's current shape) — defer the hard flip until the field matrix is proven un-emittable via stdout

**Recommendation:** the toggle-backed path (option 3) as the buildable default, and a Tom ruling on whether the flip-back gate is actually MET — the architect should not self-certify a deliberately-gated decision. If the field matrix genuinely cannot ride stdout capture, flip to native; otherwise the frozen stdout path stands.

**Why it's genuinely open (not already settled):** This was baked 'resolved' in wave-2 by self-certifying the jul9 flip-back gate on an internally-invented requirement (the §9 15-field matrix is the plan's own), but the cited frozen sources partly REFUTE the 'StandardOutput=journal yields only MESSAGE' premise: SPEC.md:682-684 explicitly calls journald 'observability, not load-bearing memory', and DECISIONS.md:137 / SPEC.md:685 state the current mechanism ALREADY emits the structured TALLY_* fields via StandardOutput=journal stdout capture. Reversing a gated frozen decision by inventing the requirement that supposedly meets the gate is over-resolution; per the triage audit it must reach Tom, not be hidden.

## CD-19 — On pool-return for a pool-vanished row, does recover() AUTOMATICALLY re-present it (reusing the existing RepresentPlan), or only mark it eligible for a separately-triggered re-present? This sits exactly on the NOT-list boundary: auto-re-presentation edges toward orchestration-in-the-binary.

**Options:**
- auto-re-present on pool-return, gated behind a per-pool `autoResume` flag defaulting ON for resource-loss (recommended — reuses RepresentPlan, adds no DAG/coordination plane)
- mark-eligible-only; re-present requires an explicit operator or harness trigger (maximally conservative on the NOT-list)
- auto-re-present unconditionally (simplest, but hardest to argue stays a mechanism not a policy)

**Recommendation:** auto-re-present gated behind a per-pool `autoResume` flag (default on for resource-loss): it reuses the exact RepresentPlan recover() already produces (row re-presentation, not origination — R16) and introduces no new coordination surface, so it is defensibly a mechanism; the flag lets a cautious host opt into mark-eligible-only.

**Why it's genuinely open (not already settled):** PS#9 settles GENERAL recover() semantics (re-present, never replay) but ONLY for daemon boot; no frozen source (DECISIONS/SPEC/prototype) and no july14 turn mentions a resource-loss verdict or pool-return as a re-present trigger — all seven triage lenses returned open. Because the trigger sits on the sovereign NOT-list line (workflow-agnostic dumb utility vs orchestrator), the architect must not move it unilaterally; this is Tom's call, not a bikeshed.

# Open-risk register

> Residual risks the deliberation named but did not (and should not yet) resolve — for awareness before implementation, not decisions.

1. dmem is frontier on THREE axes at once: kernel dmem.max had a reclaim gap (LWN #1072437); systemd DeviceMemoryMax is an OPEN DRAFT PR #37079 that force-pushes; and the Strix Halo unified-memory (carveout+GTT) topology means amdgpu dmem-region accounting is unexercised. Mitigations: observe-and-report before confine, read-back dmem.current, loud startup assertion, remote enforce as a negotiated capability (R27), and worker-side confinement mechanized on a declared servingSlice delegated cgroup (R27/§2.1a). The rung is still unproven end-to-end.
2. The pinned-commit systemd overlay must be re-cut on every PR #37079 force-push; the D-Bus property name/shape may change before merge, breaking enforce=dmem hosts until the overlay + the binary's property probe + the negotiated capability token are updated in lockstep.
3. Rewrite tax residual: cooperative-yield now has a DEFINED channel (poll-a-lease-flag + hard-reclaim → preempted, R29) but it is a BEHAVIOUR change from the Bun SIGUSR1 mechanism, so the golden-oracle (BS-13) cannot validate it — only the net-new BS-14 conformance suite can. A subtly-wrong yield checkpoint could pass every artifact diff while regressing latency/starvation; BS-14 must assert the timing bound, not just the artifact.
4. Blast-radius is BOUNDED, not merely disciplined (R31): the fsync-before-ack core is enumerated (admission+lease+verdict-fsync ONLY), the replica commit and attestation appends are OUTSIDE it, and — now reconciled with PS#9 (R13) — the post-ack replica commit is crash-safe because the sqlite file is a rebuildable cache, not a second source of truth. A slow-sqlite fault-injection test (BS-14) asserts the socket keeps accepting AND that a row lost in the ack→commit window rebuilds. Residual: the enumeration is a code-review invariant with no compiler enforcement, so it can still drift — a forbidden-in-core lint or a wrapper type would harden it.
5. taskchampion crate version is a silent cross-repo compatibility contract: the embedded replica and any stock `task` viewer read the SAME sqlite file. ReadOnly is enforced for the viewer as write-race avoidance (R13/R31) and the file is a rebuildable cache (PS#9), so a lost/rebuilt cache is safe — but a newer embedded taskchampion could still trigger a schema upgrade an older installed `task` cannot open. Needs a version-pin assertion in the module (BS-2 note); migration bidirectionality across versions is unverified from the crate source.
6. Resource-loss classification requires SUSTAINED unreachability (hysteresis, N consecutive failed probes, R26) to distinguish a true broker-vanish from a network blip or a leaf's own upstream timeout, and execution is pinned coordinator-local so recover() reaches the unit with local facts. Residual double-run risk survives only if a blip outlasts the hysteresis window AND dedup-by-existence + epoch fencing both miss — narrow, but the hysteresis constant is a tuning knob whose right value is workload-dependent and unproven.
7. Boundary-discipline is now STRUCTURAL but no longer over-tight: jobs MAY enqueue jobs (R28, the settled OCR-firehose shape), gated by server-side depth/fan-out/dedup guardrails with --parent auto-stamped; the 'must never enqueue' constraint is a per-leaf noEnqueue capability carried only by the advisory recovery assessor (task-0), and task-0's output routes to the attestation chain, not events/ enqueue (R24). The one remaining policy-vs-mechanism judgment is CD-19 (does recover() AUTO-re-present the resource-loss row on pool-return, or only mark eligible) — surfaced to Tom precisely because it sits on the NOT-list line. Residual: the depthCap/fanoutCap defaults (3/64) are guardrail constants whose right values are workload-dependent.
8. Coordinator-switch recovery for REMOTE leases is a distinct path (R30: epoch-keyed grace window + re-adopt-by-bumped-epoch + worker-refuses-to-regrant-a-live-adopted-lease), not conflated with local unit adoption. Residual: the grace window (lease.graceSec, default 90s) assumes the switch completes within it; a slow rebuild that outlasts graceSec still loses the lease. Unverified against an actual mid-job switch cycle — BS-14 exercises it in simulation only.
9. Fleet witness unification holds only while execution stays coordinator-resident (single-writer-per-host verdict chain, the explicit R26 model). The attestation chain (R24) is separately per-writer and cross-host by design. If per-host LABOR ever grows, cross-host standup becomes a federated read over per-host verdict chains — a deferred read-side feature; the assumption is load-bearing for 'one tally query log enumerates everything'.
10. The golden-oracle governs ONLY the surviving frozen surface (R23/BS-13); the net-new fleet/reboot surface — cross-host lease negotiation, resource-loss classification, pool-return ROW re-presentation, coordinator-switch re-adoption, cooperative-yield timing, remote-dmem downgrade + servingSlice stamp, job-enqueue guardrails — has NO Bun oracle and is covered solely by the non-oracle BS-14 conformance suite. That suite is fault-injection in simulation; the never-exercised real cross-box worker path means BS-14's fidelity to true fleet behaviour is itself an assumption.
11. Forgery is closed by construction (R24 two-ledger split: only the in-process core writes verdict lines; witness append/emit writes the separate attestation chain, excluded from canonical metering). Residual: consumers of `query`/standup must be disciplined to read the VERDICT chain for canonical numbers and treat attestations as advisory — the separation is enforced in the writer, not yet in every reader; if a future reader conflates the two chains, advisory attestations re-enter metering.
12. The worker-side servingSlice confinement (R27) assumes the foreign VRAM-serving process (llama-swap) can be placed under a tally-delegated slice with Delegate=yes and that the worker instance has permission to write dmem.max to that cgroup. This delegation model is stated but unverified against a real llama-swap deployment; if the serving process cannot be relocated under the slice, remote enforce=dmem degrades to advisory on that host.
13. CD-17 (native journald socket vs the deliberately-gated jul9 StandardOutput=journal decision) is surfaced to Tom rather than baked, because the frozen record (SPEC:682-689) partly refutes the 'only MESSAGE' premise the wave-2 bake rested on. BS-8 keeps a StandardOutput=journal fallback buildable behind a toggle, so the emission path is not load-bearing on the unresolved decision — but if Tom overturns the flip-back, the 15-field TALLY_* read-time joins (§9) must be re-validated against whatever the stdout-capture path can carry.
