# tally — the v0.1 path (post-build sequence)

> Ruled 2026-07-09. These are **Tom-executed** steps that begin **after** the v0 build lands.
> The build's definition of done is only **"the code exists on GitHub"** — explicitly **NOT** a
> release (the v0 build is comprehensive/fully-featured, never stubbed; see docs/BUILD-SEQUENCE.md).
> This doc records the operator sequence from "code on GitHub" → first real drive → first release;
> it does **not** re-describe what the build lands (that is BUILD-SEQUENCE.md's territory).

Ordered, Tom-executed. Each is a manual sitting on the running system, not a build step.

## 1. Absorb tally into the dotfiles

Pin tally into the dotfiles repo as a **flake input + `homeManagerModules.tally`**, per the boundary
contract (DECISIONS Q1: the flake-input + homeManagerModule pattern is THE packaging channel; the
module is load-bearing — units + pls pool config — which a bare pkg can't deliver). No bespoke
dotfiles `pkgs/tally.nix`. This is the consumption side of BUILD-SEQUENCE step 1's `inputs.tally.url`.

## 2. Rebuild the system to latest dotfiles

`nixos-rebuild switch --flake` to bring the box to the newest dotfiles state — tally's daemon +
CLI + pls broker units live once the module is imported and switched (`role`/`conductorHost`, the
minimal option set). Composes into the dotfiles-provided zmx substrate (BUILD-SEQUENCE step 7);
tally generates none of it.

## 3. Test-drive on the academic-PDF OCR pass

Run the ~4.7k-sidecar daily OCR drain as a **real tally job** — the first-class spawn-tracked-agent-job
path (BUILD-SEQUENCE step 3), not a filesystem-drain codepath (PS#1). Proves the job → pls lease →
worker-pinned OCR → witness → artifacts-to-git path end-to-end on live hardware. Acceptance is the
BUILD-SEQUENCE step 3/5 shape observed on Tom's own daily drain: enqueue via a trigger surface, OCR
runs only on the worker, the witness/TaskChampion log records which papers ran and when, and re-runs
skip already-transcribed papers.

## 4. Put the release flow in place

Once the drive clears: stand up the release ritual on the GitHub repo — **release-please** driving
**mecattaf.dev** personal-blog updates. This follows the notes-repo technical-project-morph protocol:
repo → conventional commits → release-please → gate-awaiting blog post → socials, where the blog gate
is **mechanical evidence** (the release tag), not a hand-authored trigger. The blog post updates off
the tag; socials follow the post.

## 5. Cut v0.1

Release **v0.1** (or whatever semver the release-please / conventional-commits convention encourages)
and watch the blog post update in parallel off the tag. **Naming stays deferred to the release ritual**
— the string "tally" is a working handle; the final name is fixed at this ritual, not before (per the
standing DECISIONS naming-deferral; nothing in the build freezes a name — cf. Q9, no identifier frozen
in the docs).

## 6. Use the release to test publishing surfaces

Drive the cut v0.1 through the different platforms Tom publishes his work on — the release is the first
real payload for exercising those surfaces end-to-end.
